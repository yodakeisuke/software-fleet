# 事実（イベント）と軸

一つの筋（ある 1 件分の実例）を選び、その筋の事実を時間の順に並べる。気づき（矛盾・欠落・疑問）は、その場で盤面に反映する。

## 事実の見極め方
- 過去形で言えるか
- システムの状態を変えた事実か。何も記録しない閲覧・検索は事実ではない（閲覧でも、記録が残り後の表示や判断に効くなら事実）
- 業務の言葉か（DB 操作の言葉ではない）

## 軸の筋の通し方
- 順序の矛盾 — 例: チェックインが予約より前（ウォークインという別の筋の発見に転じることもある）
- 前提の欠落 — 例: 部屋が予約されたのに、部屋が登録された事実がない
- 状態を変えない出来事の混入 — 例: 「カレンダーを見た」はリードモデルの仕事
- 事実として曖昧 — 例: 「予約が更新された」は、キャンセルか延泊か分からない

## 落とし穴
- CRUD 命名 — 「注文が更新された」では、何が起きたかを語れない
- 属性ごとの事実 — 「名前が変わった」のような細かい事実が増える
- 事実の体裁をした指示 — 「牛乳がなくなった」は、実質「牛乳を買え」
- 画面の中だけで変わる状態（選択中・下書き）を事実にする — それはスケッチに描く
- 分岐や例外を軸に描き込む — 軸はハッピーパス 1 本。却下・失敗は起きえた別の結果、振る舞いを持つ失敗は別の流れへ
- 起点が違う話を同じ軸に混ぜる — 例: 既存顧客からの引き合いは別の筋

ドメインの人がつまずいた箇所が、設計の穴。
