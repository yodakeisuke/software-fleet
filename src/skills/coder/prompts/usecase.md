# 業務手順書（ユースケース記述）
集約のコマンド 1 つ・クエリ 1 つに 1 枚。
- command: 状態を変える。成功 = 起きた出来事で、write がそれを記す
- query: 状態を読んで見せるだけ。成功 = 見せるもの（一覧・詳細）。write も状態の遷移も無い

集約が同じなら、作成・編集・停止の手順書は同じ用語集を見る ― 内容を作る関数も、遷移表も、write も 1 つを共有する。

## I/O
業務の入力と成果物を、成功とエラー終了のそれぞれについて網羅する。
- in = 入力（command の依頼 / query の条件）、out = 終わり方（成功を先頭に、続けて失敗）
- action = 外部に影響を与える読み書き（副作用）。read = 状態を読む（readmodel）、write = 状態を書く（readmodel への投影や外部書き込み）
- 台帳 = 紙の帳簿なら何を残すか。状態機械の今（状態）、起きた出来事の記録、query が見せる一覧表。欄は用語集の型と似ていても別に書く（型 = ロジックの I/O、欄 = 残す属性）
- 表が拒否とする遷移を、再送や同時実行でも通さないのは write の責務

## SOP（業務手順）
「流れ」だけを書く。domain logic に相当する粒度の記述は一切書かない。業務の言葉で、何をどういう手順で行うかを書く ― 実装上は domain logic と外部アクションのオーケストレーションになる。

分岐は書かない ― 行は全てコンビネータで連結する（railway はその一例に過ぎない）。道は 3 本で、1 本目以外は値で表す: メイン = 行の列。代替 = 成功の直和 ― 次の行が変種ごとに受けて本線へ合流する。業務エラー = 失敗で出口へ ― 予期した業務の終わり方で、システムの例外ではない（例外はコンピュータの話なので書かない）。条件付きのアクションは、アクションを値で受け取る logic の中で呼ぶ。
