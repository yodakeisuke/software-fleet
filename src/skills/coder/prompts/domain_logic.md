# 業務ロジック
domain logic は 3 類型。1 つの関数はどれか 1 つの責務だけを負い、記述内容は互いに排他である。
- 計算: 1 つの計算・算出・データ加工だけ。分岐を書かない ― 値で分かれるなら表を引き、求め方で分かれるなら判断が計算を返す
- 判断: 表のような決定ロジックだけ。実装はパターンマッチ、テストはディシジョンテーブル。因子の水準は有限 ― 有限でない値（個数）は計算で直和にしてから受ける。判断は値を作らない
- 遷移: usecase をまたぐ状態の遷移だけ。契機 = コマンドの直和、出来事 = 起きたことの直和（write はこれを記す）。表に無い（状態, 契機）は拒否。実装は状態の直和型と遷移関数、テストは状態遷移テスト

関数は値である。判断が計算を受け取って実行する、計算が判断を受け取る、判断が計算を返す ― はどれも頻出。パラメトリック多相でも考える。
domain logic は純粋で、外（台帳など）を読まない。副作用を起こす関数を受け取って実行することはできる。

## モデル = 型と不変条件
モデルは型で書き、3 類型はその型の値を作る関数である。形は持つ要素で分かれ、不変条件は全てが持つ。

| Logic | Form | Invariant | Variants | Morphism | Signature |
|---|---|:-:|:-:|:-:|---|
| Computation | Value | ✓ | — | — | `Input → Value` |
| Decision | Kind | ✓ | ✓ | — | `Factors → Variant` |
| Transition | Lifecycle | ✓ | ✓ (State) | ✓ | `(State, Trigger) → Event \| Rejection` |

- モデルは入れ子になる。変種の付随情報も、値の部品も、状態の中身も、それ自体がどれかの形のモデル。層をまたぐ不変条件は外の作り手が守り、中は作られた型として受け取る。中の状態機械の出来事は、外の契機になる
- 不変条件は常に守るべきビジネスルール。型の形で封じられるものは形で封じる ― 無効な組み合わせを表せなくする。付随情報が種類で決まるなら直和にする。形で封じきれないものは型に書かず、型を作る関数が守り、破れる形ごとに失敗の変種を立てて検める
- 型はそれを通った証（parse, don't validate）。作り手を通らずにその型の値は生まれない。外から入る型は未検証。定義に過ぎない文は不変条件ではなく、用語の説明に回す
- 既存コードには、型になっていない暗黙のモデルがある。名前を付けて型と表に起こす。到達できる無効は要素ごとにある: 不変条件を破った値、作り手を通らない値、変種の外の値、表に無い遷移。直すのは型で封じるのが先で、検査を足すのは後
- 再送は、出来事の後の状態に同じ契機が来ること。同時実行は、古い状態を読んだまま契機を当てること。どちらも遷移の行で、特別扱いしない

## モジュール化
用語 = モジュール。凝集性を上げるという一般論の通りに設計し、外部に公開する境界面（手順書が名指す logic）は数も広さも最小にする。既存コードにある語は再発明しない。
